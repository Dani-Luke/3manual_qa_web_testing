# Тест-дизайн формы регистрации

## 1. Цель

Цель тест-дизайна — определить минимальный, но достаточный набор тестовых данных для проверки валидации полей формы регистрации.

В проекте использовал две техники:

* **Equivalence Partitioning (EP)** — разбиение входных данных на классы эквивалентности;
* **Boundary Value Analysis (BVA)** — анализ граничных значений.

## 2. Требования к полям

| Поле     | Требование                                         |
| -------- | -------------------------------------------------- |
| Username | обязательное, от 3 до 20 символов                  |
| Email    | обязательное, корректный формат email              |
| Password | обязательное, от 8 до 20 символов                  |
| Age      | обязательное, целое число от 18 до 65 включительно |

---

## 3. Username

### 3.1 Классы эквивалентности

Допустимый диапазон: **от 3 до 20 символов**.

| Класс | Диапазон          | Ожидаемый результат  | Пример                  |
| ----- | ----------------- | -------------------- | ----------------------- |
| EP-01 | менее 3 символов  | Ошибка валидации     | `ab`                    |
| EP-02 | 3–20 символов     | Значение принимается | `alex123`               |
| EP-03 | более 20 символов | Ошибка валидации     | `abcdefghijklmnopqrstu` |

### 3.2 Анализ граничных значений

Для нижней границы **3 символа** проверяются значения:

* 2 — ниже границы;
* 3 — граница;
* 4 — выше границы.

Для верхней границы **20 символов**:

* 19 — ниже границы;
* 20 — граница;
* 21 — выше границы.

| Значение | Относительно границы | Ожидаемый результат |
| -------: | -------------------- | ------------------- |
|        2 | ниже нижней границы  | Ошибка              |
|        3 | нижняя граница       | Успешно             |
|        4 | выше нижней границы  | Успешно             |
|       19 | ниже верхней границы | Успешно             |
|       20 | верхняя граница      | Успешно             |
|       21 | выше верхней границы | Ошибка              |

### 3.3 Тестовые данные

* `ab` — 2 символа;
* `abc` — 3 символа;
* `abcd` — 4 символа;
* `abcdefghijklmnopqrs` — 19 символов;
* `abcdefghijklmnopqrst` — 20 символов;
* `abcdefghijklmnopqrstu` — 21 символ.

* `user@`;

## 6. Age

Допустимое значение: **целое число от 18 до 65 включительно**.

### 6.1 Классы эквивалентности

| Класс | Диапазон / тип  | Ожидаемый результат  | Пример |
| ----- | --------------- | -------------------- | ------ |
| EP-01 | менее 18        | Ошибка валидации     | `17`   |
| EP-02 | 18–65           | Значение принимается | `30`   |
| EP-03 | более 65        | Ошибка валидации     | `66`   |
| EP-04 | нецелое число   | Ошибка валидации     | `18.5` |

### 6.2 Анализ граничных значений

Для нижней границы **18**:

* 17 — ниже границы;
* 18 — граница;
* 19 — выше границы.

Для верхней границы **65**:

* 64 — ниже границы;
* 65 — граница;
* 66 — выше границы.

| Значение | Относительно границы | Ожидаемый результат |
| -------: | -------------------- | ------------------- |
|       17 | ниже нижней границы  | Ошибка              |
|       18 | нижняя граница       | Успешно             |
|       19 | выше нижней границы  | Успешно             |
|       64 | ниже верхней границы | Успешно             |
|       65 | верхняя граница      | Успешно             |
|       66 | выше верхней границы | Ошибка              |

Значение `18.5` проверяется отдельно как представитель класса нецелых значений.

### 6.3 Тестовые данные

* `17`;
* `18`;
* `19`;
* `30`;
* `64`;
* `65`;
* `66`;
* `18.5`.

## 7. Проверка обязательности полей

Все четыре поля являются обязательными.

Для каждого поля проверяется отправка формы без значения:

| Поле     | Тестовое значение | Ожидаемый результат |
| -------- | ----------------- | ------------------- |
| Username | пусто             | Ошибка              |
| Email    | пусто             | Ошибка              |
| Password | пусто             | Ошибка              |
| Age      | пусто             | Ошибка              |

## 8. Позитивный сценарий

Для проверки успешной регистрации используется набор допустимых значений:

| Поле     | Значение           |
| -------- | ------------------ |
| Username | `alex123`          |
| Email    | `user@example.com` |
| Password | `password123`      |
| Age      | `30`               |

### Ожидаемый результат

Форма успешно отправляется, отображается сообщение:

`Registration successful.`

---

## 9. Негативные сценарии

Основные негативные проверки:

* пустое обязательное поле;
* Username короче 3 символов;
* Username длиннее 20 символов;
* некорректный формат Email;
* Password короче 8 символов;
* Password длиннее 20 символов;
* Age меньше 18;
* Age больше 65;
* Age содержит нецелое значение.

При обнаружении некорректного значения форма не должна успешно отправляться, а соответствующее поле должно отображать сообщение об ошибке.

---

## 10. Итог

Применение Equivalence Partitioning позволило сократить количество проверок за счёт выбора представителей различных классов входных данных.

Boundary Value Analysis использовал для проверки значений непосредственно **до границы, на границе и сразу после границы**.

Для ограниченных диапазонов в проекте проверяются:

* Username: 2, 3, 4, 19, 20, 21 символ;
* Password: 7, 8, 9, 19, 20, 21 символ;
* Age: 17, 18, 19, 64, 65, 66.

Дополнительные классы, не описываемые только числовыми границами, проверяются отдельно. Например, для Age проверяется `18.5`, поскольку возраст по требованиям должен быть целым числом.

На основании требований сформирован набор тестовых данных для позитивных, негативных и граничных сценариев.
